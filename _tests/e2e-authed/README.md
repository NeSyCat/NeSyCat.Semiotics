# Authenticated E2E tests (Playwright + a LOCAL Supabase stack)

Real-browser E2E specs over the `/editor` React Flow canvas as an
**authenticated** user — sidebar CRUD, first-login org bootstrap,
invitations, and two-client Realtime sync. Everything here runs against a
**local** Supabase stack (Docker) and **never** the remote/production
project from the repo's own `.env.local`. See `_tests/e2e/README.md` for
the sibling **anonymous** lane (no auth, no DB, no Docker) — that lane is
untouched by anything in this directory.

## Prerequisites

- Docker running locally (Docker Desktop, Colima, OrbStack, …).
- The Supabase CLI (`devDependency "supabase"` — already installed via
  `npm ci`/`npm install`, invoked here as `npx supabase` under the hood).
- Nothing else. `psql` is **not** required — see `lib/bootstrap-db.ts`'s
  header comment for why (it uses `pg`, already a runtime dependency,
  instead of shelling out to the system `psql` binary).

## One-command local run

```sh
npm run test:e2e:authed
```

This runs `test:e2e:authed:setup` (below) first, then the Playwright
`authed-setup` + `authed-chromium` projects.

```sh
npm run test:e2e:authed:setup   # just the bootstrap, if you want to iterate
npm run test:e2e:authed:ui      # same, then Playwright's UI mode
```

`test:e2e:authed:setup` (`scripts/setup.ts`) is idempotent to re-run and does,
in order:

1. **`ensureLocalStack()`** (`lib/local-stack.ts`) — checks whether THIS
   project's local Supabase stack (`supabase status -o env`, run from
   `_concept/04-data-schema` per the root CLAUDE.md's CLI cwd quirk) is
   already up; starts it (`supabase start`) if not. If Docker isn't
   running, or another local Supabase project already holds one of the
   fixed ports from `_concept/04-data-schema/config.toml` (54321-54324),
   this fails with an explicit, actionable message — it will **not** start
   Docker for you, and will **not** stop another project's containers for
   you (that decision is left to you, on purpose).
2. **`bootstrapDatabase()`** (`lib/bootstrap-db.ts`) — mirrors
   `.github/workflows/preview-db.yml`'s step order exactly: `prisma contract
   emit` → `prisma/sql/01-functions.sql` → `prisma/sql/00-preflight.sql` →
   `prisma db verify` (three-way route: fresh DB → `db init -y`; signed →
   `db update -y --advance-ref db`; anything else → abort) →
   `prisma/sql/02-guards.sql` → `prisma/sql/03-realtime.sql` (the
   Realtime publication — without it no `postgres_changes` event fires at
   all, even with everything else correct). Every `prisma` invocation gets
   `PRISMA_DB_URL` set to the LOCAL stack's connection string in its own
   child-process env, which `prisma/prisma.config.ts`'s `db.connection`
   prefers over `.env.local`'s (remote) `DIRECT_URL` — see that file's own
   `PRISMA_DB_URL ?? DIRECT_URL` line and `lib/bootstrap-db.ts`'s comment on
   `runPrisma()`.
3. **Seeds two fresh users** (`lib/seed-users.ts`) via the local stack's
   admin API (service-role key) — a primary (org owner) and an invitee.
   Fresh, random-suffixed emails **every run** (not fixed fixtures) so
   `bootstrap.spec.ts`'s "first login" assertion is genuinely true every
   time, not just the first time this script ever runs against a given
   local Postgres volume.
4. **Writes `.env.test.local`** at the repo root (`lib/env-file.ts`) — see
   "How this stays off the remote database" below.
5. **Writes `.generated/stack.json`** — local stack URLs/keys + both
   users' credentials, consumed by `auth.setup.ts`.

## How this stays off the remote database — twice over

1. **`.env.test.local` + `NODE_ENV=test`.** Next.js's env loader
   (`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`,
   "Environment Variable Load Order") skips `.env.local` **entirely** when
   `NODE_ENV=test`, checking `.env.$(NODE_ENV).local` first. The authed
   `next dev` (`playwright.config.ts`'s second `webServer` entry) is started
   with `env: { NODE_ENV: 'test' }`, so the real `.env.local` — which points
   at the production Supabase project — is never even opened by that
   process; `.env.test.local` (gitignored, generated by step 4 above) wins
   outright.
2. **`assertLocalHost()`** (`lib/safety.ts`). Every connection string /
   API URL this lane is about to *use* (not just read) — the DB URL handed
   to `prisma`/`pg`, the API URL handed to the admin/sign-in clients —
   passes through this guard first, which throws if the host isn't
   `127.0.0.1`/`localhost`/`::1`. Defense in depth against a wiring mistake
   anywhere upstream ever resolving to the remote project.

## Playwright wiring (`playwright.config.ts`)

A completely separate `testDir` (`_tests/e2e-authed`), project set, port
(3220, vs the anonymous lane's 3210), and `webServer` entry from the
anonymous lane — all gated behind `E2E_AUTHED=1`. With that env var unset
(i.e. `npm run test:e2e`), none of it is evaluated: no second dev server, no
Docker/Supabase dependency, byte-for-byte the same anonymous run as before
this ticket.

Two projects when `E2E_AUTHED=1`:

- **`authed-setup`** — matches `*.setup.ts` (`auth.setup.ts`), runs first.
- **`authed-chromium`** — matches `*.spec.ts`, `dependencies: ['authed-setup']`.

Deliberately **not** wired through Playwright's own `globalSetup` hook:
that hook runs *after* `webServer` has already been started (confirmed by
reading `playwright/lib/runner/index.js`'s task ordering —
`createPluginSetupTasks` before `config.globalSetups`), which would be too
late to have `.env.test.local` on disk before `next dev` reads its env
files once at boot. `test:e2e:authed` instead chains the setup script and
`playwright test` with a plain shell `&&`.

## How session injection works (`auth.setup.ts` + `lib/session-cookie.ts`)

The app is **OAuth-only** — `lib/auth.ts`'s `startGitHubSignIn` is the only
sign-in entry point (`app/auth/callback/route.ts` handles the PKCE
exchange). There is no password form to drive through the UI. Per the
ticket, `auth.setup.ts` instead:

1. Signs in with `@supabase/supabase-js`'s `signInWithPassword` directly
   against the **local** stack's auth API (the two users seeded above).
2. Hand-builds the exact cookie(s) `@supabase/ssr`'s `createServerClient`
   (`lib/supabase/server.ts`, `lib/supabase/proxy.ts` — the middleware that
   calls `supabase.auth.getUser()` on every request) and `createBrowserClient`
   (`lib/supabase/client.ts`) expect, via `BrowserContext.addCookies()`.
3. Confirms the app's own middleware actually honors it — navigates to
   `/editor` and waits for the real redirect into `/editor/<uuid>`
   (`app/editor/page.tsx`'s own logic, not a mock) — before saving
   `storageState`.

**Exactly how the cookie name/value were derived** — every detail read out
of the installed `node_modules/@supabase/ssr` and `@supabase/supabase-js`
source, not guessed — is documented in full in `lib/session-cookie.ts`'s
header comment. Summary:

- **Name**: `sb-<ref>-auth-token`, where `<ref>` is
  `new URL(supabaseUrl).hostname.split('.')[0]` — supabase-js's own default
  `storageKey` computation. For the local stack's `http://127.0.0.1:54321`,
  that's `sb-127-auth-token` (a well-known local-dev quirk).
- **Value**: `"base64-" + base64url(JSON.stringify(session))` —
  `@supabase/ssr`'s default `cookieEncoding: "base64url"`, applied to the
  GoTrueClient session object (exactly `signInWithPassword`'s
  `data.session`).
- **Chunking**: `@supabase/ssr` splits into `name`, `name.0`, `name.1`, …
  past 3180 encoded characters. A base64url string is already outside
  `encodeURIComponent`'s escape set, so plain-length chunking is exactly
  equivalent here — no UTF-8-boundary logic needed.
- **Attributes**: `path=/`, `sameSite=Lax`, `httpOnly=false`, 400-day
  `maxAge` (`@supabase/ssr`'s `DEFAULT_COOKIE_OPTIONS`), domain = the authed
  webServer's own host (`localhost`), **not** the Supabase API host.

Two storageState files land in `.generated/auth/` (gitignored):
`primary.json` (the `authed-chromium` project's default — see
`playwright.config.ts`) and `invitee.json` (loaded explicitly by
`invitations.spec.ts` via `browser.newContext({ storageState: ... })`).

## What's covered

- **`bootstrap.spec.ts`** — first-login org bootstrap (`getMe()`'s
  bootstrap branch) holds: exactly one, owned, personal organization; and
  `/editor` redirects into a real diagram.
- **`sidebar.spec.ts`** — create (lands on the new diagram, appears in the
  list), rename (instant optimistic title, persists after reload), and
  delete: the open tab navigates away, while a *second*, non-open tab sees
  the row vanish **via Realtime**, confirmed gone after reload too (this UI
  has no "select without opening" affordance — see that file's own comment
  for why "delete a non-open diagram" is necessarily a two-tab, realtime
  scenario here, not a single-tab one).
- **`invitations.spec.ts`** — drives the real invite UI
  (`components/OrgSettings.tsx`, opened from `UserMenu`'s owner-only gear;
  feasible headless since the optional Brevo notification email degrades
  gracefully with no SMTP configured — see the root CLAUDE.md's
  "Invitation emails" section). The invitee's own first `/editor` visit
  auto-accepts (`getMe()` accepts pending invitations *before* its
  bootstrap branch, so the invitee joins the shared org instead of getting
  a personal one); the owner's roster shows the invitation gone and a real
  member row in its place.
- **`realtime.spec.ts`** — two browser contexts of the SAME user: a
  sidebar rename made in one appears in the other without a reload, and a
  shape added to the canvas in one appears in the other for the same open
  diagram. This is the authenticated, two-client Realtime coverage
  `_tests/e2e/README.md`'s own "Realtime" section flags as missing from the
  anonymous lane (which runs fully unauthenticated, so every realtime hook
  there no-ops by construction).

## CI

`.github/workflows/e2e.yml`'s `e2e-authed` job runs this lane on
`ubuntu-latest` (Docker pre-installed) via `supabase/setup-cli`, chromium
only, as a job fully independent of the existing `e2e` (anonymous) job.
